# 改用 Supabase 收集資料：規劃書

> 狀態：**實作中**。操作步驟見 [supabase-setup.md](supabase-setup.md)。
>
> 已確認的決定：先用 Free 方案試；「環保限制」→ 部分停機、「測試運轉」→ 試運轉；
> GitHub Actions 改成「備援＋警報」。

## 0. 為什麼要換？

| 問題 | 現在（GitHub Actions） | 換成 Supabase 後 |
|---|---|---|
| 排程準不準 | GitHub 免費排程「盡力而為」，忙的時候會延遲、跳過。11 小時只收到 3 筆 | pg_cron 跑在你自己的資料庫裡，時間到就執行，不用排隊 |
| 資料存在哪 | 每筆資料都 commit 進 git，一年 5 萬多個 commit，repo 會越來越肥 | 存進資料庫，可以直接用 SQL 查詢、給網站讀 |
| 出問題怎麼知道 | 只能自己翻 commit 紀錄 | 每次執行都寫進「收集紀錄表」，缺了哪個時間點一查就知道 |

最重要的原則：**台電歷史資料沒有「備註」和「裝置容量」，漏掉就補不回來。**
所以整個設計的重點是「多給自己幾次機會」和「漏了要馬上知道」。

## 1. 資料庫設計

### 1-1. 整體架構（共 5 張表）

```
units（機組清單）──┐
                   ├──> readings（每 10 分鐘的發電紀錄）──> daily_unit_stats（每日彙總）
remark_rules（備註分類規則）─┘
collection_runs（收集紀錄，出問題時查這張）
```

另外，台電原始 JSON 檔壓縮後存在 **Supabase Storage**（類似雲端硬碟），
路徑和現在一樣：`raw/2026-11-10/1140.json.gz`。

**為什麼原始檔還要另外存？** 資料庫裡是「整理過」的資料。萬一哪天發現整理的
程式有 bug（例如機組改名沒處理好），可以從原始檔重新整理一次。原始檔就是保險。

### 1-2. `units`：機組清單

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | smallint，自動編號 | **固定編號**，例如 1、2、3…。一旦給了就不會變 |
| `type` | text | 類型，例如「風力」 |
| `name` | text | 名稱（去掉「(註10)」之後），例如「沃一風」 |
| `is_renewable` | boolean | 是否為再生能源（太陽能、風力、水力、其它再生能源） |
| `footnote` | text | 最近一次看到的註記編號，例如 "10" |
| `first_seen_at` / `last_seen_at` | timestamptz | 第一次／最後一次出現的時間 |

- 「類型 + 名稱」設成**不能重複**，跟 `clean_data.py` 的 `unit_id = "風力|沃一風"` 是同一個規則
  （因為太陽能和風力都有一列叫「其它台電自有」，只看名稱會搞混）。
- **為什麼要用數字編號，不直接用「風力|沃一風」？** 發電紀錄表會有上千萬列，
  每列存一個 2 bytes 的數字，比存一串中文字省很多空間，查詢也比較快。
- **新機組怎麼辦？** 收集程式發現沒看過的機組，會自動新增一列，不需要你手動處理。
- 目前資料共 **191 個機組**（再生能源 107 個）。「小計」和「儲能負載」列跟現在一樣去掉。

### 1-3. `readings`：每 10 分鐘的發電紀錄（最大的一張表）

| 欄位 | 型別 | 說明 |
|---|---|---|
| `observed_at` | timestamptz | 台電資料時間（例如 2026-11-10 11:40 台灣時間） |
| `unit_id` | smallint | 對應 `units.id` |
| `capacity_mw` | real | 裝置容量(MW)，台電寫「-」就存空值 |
| `output_mw` | real | 淨發電量(MW)，台電寫「N/A」就存空值 |
| `status_id` | smallint | 狀態代碼（見 1-5），**由資料庫依備註自動填** |
| `remark` | text | 原始備註（只去掉前後空白，" " 統一成 ""） |

- **同一時間點同一機組不能重複**：把 `(observed_at, unit_id)` 設成主鍵（primary key）。
  資料庫會直接拒絕重複的資料，所以就算收集程式跑了兩次、或兩個收集程式同時在跑，
  也只會存到一份。這讓我們可以放心地「多抓幾次」。
- **為什麼用 real 存數字？** real 是 4 bytes 的小數。台電數字只有一位小數，real 精度足夠，
  而且比 numeric 省空間。（最大的一列是「其它購電太陽能」約 15,112 MW，real 存得下。）
- 不另外存「淨發電量/裝置容量比(%)」：它可以用前兩個欄位算出來。

### 1-4. 時區：統一用台灣時間

- 時間欄位用 **timestamptz**（帶時區的時間）。它記錄的是「絕對時間點」，不會搞混。
- 台電的 `DateTime` 沒寫時區，收集程式會明確地把它當成台灣時間（+08:00）存進去。
- 把資料庫預設時區設成 `Asia/Taipei`，這樣在 Supabase 網頁上、用 SQL 查詢時，
  看到的都是台灣時間。
- 「每日」一律用台灣時間的 00:00～23:50 算一天。

**為什麼不用不帶時區的 timestamp？** 因為 Supabase、GitHub、各種雲端服務預設都是
UTC（比台灣慢 8 小時）。不帶時區的話，哪天某個程式用 UTC 寫進來，就會差 8 小時而且看不出來。

### 1-5. `remark_rules`：備註分類規則（和 availability.py 一致）

把 `availability.py` 裡的 `REMARK_RULES` 原封不動搬進資料庫：

| 狀態代碼 | 狀態 | availability 怎麼算 | 對應的備註 |
|---|---|---|---|
| 1 | 正常 | 100% | （空白） |
| 2 | 主動少發 | 100% | 配合綠電先行、友善降載減排 |
| 3 | 部分停機 | 發電量 ÷ 容量 | 部分檢修、部分歲修、部分故障、運轉限制 |
| 4 | 停機 | 發電量 ÷ 容量 | 檢修、歲修、故障 |
| 5 | 狀態不明 | 不算 | 通訊異常 |
| 6 | 試運轉 | 不算 | 新機組試俥、新增設備測試運轉 |
| 7 | 未知備註 | 發電量 ÷ 容量（保守） | 規則表裡沒有的備註 |

**設計重點：分類這件事只在資料庫裡做一次。**

- 收集程式（Edge Function）只負責「照抄」台電的原始備註，**不做判斷**。
- 資料寫進 `readings` 的那一刻，資料庫用規則表自動填上 `status_id`。
- 規則改了（例如新增一種備註），執行一個「重新分類」指令，舊資料的 `status_id`
  也會一起更新，不會有新舊規則混在一起的問題。原始備註永遠都在，所以隨時可以重算。
- 實作時會寫一個檢查程式，比對 `availability.py` 和資料庫的規則是否完全一樣。

> ⚠️ **需要你決定**：目前收到的資料裡已經出現**兩種規則表裡沒有的備註**，
> 現在都被當成「未知備註」：
>
> | 備註 | 出現在 | 我的建議 |
> |---|---|---|
> | 環保限制 | 台中 #3～#10 燃煤機組（晚上 20:20，出力約 78%） | 歸為「部分停機」，跟「運轉限制」一樣：是規定限制發不出來，不是主動選擇 |
> | 測試運轉 | 核三Gas2（沒有裝置容量） | 歸為「試運轉」，跟「新增設備測試運轉」一樣 |
>
> 決定後 `availability.py` 和 `docs/methodology.md` 也要一起更新。

### 1-6. `daily_unit_stats`：每日彙總

每個機組每天一列，主鍵是 `(unit_id, day)`。

| 欄位 | 說明 |
|---|---|
| `day` | 日期（台灣時間） |
| `unit_id` | 機組 |
| `generation_kwh` | 發電量（度）＝ 當天有資料時段的平均淨發電量(MW) × 24 小時 × 1000 |
| `availability` | 當天每 10 分鐘 availability 的平均（和 `availability.py` 的 `evaluate()` 一樣） |
| `capacity_factor` | 當天每 10 分鐘容量因數的平均 |
| `capacity_mw` | 當天最後一筆的裝置容量 |
| `intervals_present` | 當天收到幾個時間點（最多 144） |
| `intervals_valid` | 其中能算 availability 的有幾個（扣掉試運轉、通訊異常等） |
| `completeness` | 資料完整度 ＝ `intervals_present ÷ 144` |
| `flagged_remarks` | 當天出現的停機類備註和次數，例如 `{"部分檢修": 12, "檢修": 3}`，網站標註用 |
| `computed_at` | 這列是什麼時候算的 |

說明：

- **發電量為什麼用「平均 × 24 小時」而不是直接加總？** 如果漏了幾個時間點，
  直接加總會偏低；用平均乘回 24 小時比較接近真實。完整度 100% 時兩種算法結果一樣。
  完整度太低的日子（例如低於 80%），網站上應該註明。
- 抽蓄水力、儲能在抽水／充電時淨發電量是負的，發電量可能是負數，這是正常的。
- **每日彙總是「可以重算」的**：它完全由 `readings` 算出來，算錯了或規則改了，刪掉重算就好。
  - 每天 00:15（台灣時間）自動算「昨天」。
  - 每小時自動重算「今天」，讓網站可以顯示今天到目前為止的數字。
- 計算邏輯用 SQL 寫一次，實作完後會用現有的 3 筆資料，對照 `availability.py` 的結果，確認數字一樣。

### 1-7. `collection_runs`：收集紀錄

每次收集程式執行都寫一列：執行時間、來源（supabase／github）、抓到的資料時間、
新增幾列、成功或失敗、錯誤訊息。保留 90 天，自動刪除更舊的。

另外會做一個「**缺資料檢查**」的查詢：列出最近 N 天哪些 10 分鐘時間點沒有資料。

### 1-8. 安全性

Supabase 的資料表預設可以從網路上被讀寫，所以要開 **RLS（Row Level Security）**：

- 寫入：只有收集程式（用 service role 金鑰）可以寫。
- 讀取：之後做網站時，再開放 `units`、`daily_unit_stats` 給大家讀。

### 1-9. 每年會用多少空間？（實測）

我在電腦上用 PostgreSQL 16 模擬了**一整年**的資料（191 機組 × 144 次 × 365 天 = **10,038,960 列**）實際量：

| 項目 | 一年大小 |
|---|---|
| `readings` 資料本身 | 532 MB |
| `readings` 的主鍵索引（防重複、加快查詢用） | 414 MB |
| `daily_unit_stats`（191 × 365 = 69,715 列） | 約 8 MB |
| `units`、`remark_rules`、`collection_runs` | < 5 MB |
| **資料庫合計** | **約 0.95 GB／年** |
| Storage 原始檔（每個約 3.5 KB × 52,560 個） | 約 185 MB／年 |

**這對方案選擇很重要**（價格以 Supabase 官網為準）：

| | Free（免費） | Pro（約 US$25／月） |
|---|---|---|
| 資料庫空間 | 500 MB → **大約 6 個月就滿** | 8 GB → 夠用約 8 年 |
| 閒置暫停 | 一週沒有活動會被**暫停**，暫停期間 pg_cron 不會跑 = 漏資料 | 不會暫停 |
| 自動備份 | 沒有 | 每日備份 |

**我的建議**：這份資料漏了補不回來，建議用 **Pro**。如果想先免費試，可以先用 Free
跑 1～2 週把流程弄穩，確定要長期收集時再升級（升級不用搬資料）。

## 2. 資料收集

### 2-1. 流程

```
pg_cron（每 3 分鐘）
   └─> pg_net 呼叫 Edge Function「collect」
         1. 抓台電 JSON（失敗會自動重試 2 次）
         2. 整理資料（規則和 clean_data.py 一樣）
         3. 新機組 → 新增到 units
         4. 寫進 readings（重複的自動略過）
         5. 原始檔存到 Storage（已經存過就略過）
         6. 寫一筆 collection_runs
```

| 名詞 | 白話解釋 |
|---|---|
| **Edge Function** | 放在 Supabase 上的一小段程式（用 TypeScript 寫），被呼叫時才執行 |
| **pg_cron** | 資料庫內建的「鬧鐘」，可以設定每隔多久做一件事 |
| **pg_net** | 讓資料庫可以「打電話」（發 HTTP 請求）給 Edge Function |
| **Vault** | Supabase 的保險箱，用來放金鑰，避免金鑰直接寫在程式碼裡 |

### 2-2. 為什麼是「每 3 分鐘」而不是每 10 分鐘？

台電每 10 分鐘更新一次，但我們不知道它確切幾分幾秒更新。如果剛好也每 10 分鐘抓一次：

- 時間稍微錯開，就可能連續兩次抓到同一筆，然後**漏掉下一筆**。
- 只要台電網站或網路有一次不穩，那個時間點就沒了。

每 3 分鐘抓一次，每個時間點大約有 **3 次機會**。重複的資料會被主鍵擋掉，所以多抓不會出錯。
成本：一個月約 14,400 次呼叫，遠低於免費額度（50 萬次／月）。

### 2-3. 整理規則（從 clean_data.py 搬過去）

Edge Function 要用 TypeScript 重寫一次 `clean_data.py` 的規則：
去掉 BOM、去掉「小計」和「儲能負載」列、去掉類型裡的 `</b>`、名稱的「(註10)」拆出來、
「-」「N/A」轉成空值、備註去掉前後空白。

實作完後會拿現有的 3 個原始檔，比對 Python 和 TypeScript 整理出來的結果完全一樣。

## 3. 匯入目前 data/raw 的資料

repo 裡目前有 3 個時間點（2026-11-10 的 11:40、11:50、20:20），共 573 列。

做法：

1. 寫一個一次性的 Python 小程式 `import_raw.py`，用現有的 `clean_data.py` 讀檔，
   產生一個 SQL 檔。
2. 你把 SQL 檔內容貼到 Supabase 網站的 **SQL Editor** 執行。
   （這樣你不需要在電腦上設定任何金鑰。）
3. 原始 `.json.gz` 檔用網頁拖拉上傳到 Storage。

因為主鍵會擋掉重複資料，這個步驟重跑幾次都沒關係。

> ❓ **需要你確認**：`collect.py` 寫著它原本是在你的 **Mac 上用排程**跑的。
> 如果你的 Mac 上 `data/raw/` 還有沒推上 GitHub 的資料，請一起匯入（越早的資料越珍貴）。

## 4. GitHub Actions 怎麼處理

建議分兩階段：

**階段一：先並行（約 3～7 天）**
GitHub Actions 照舊跑，Supabase 同時開始收集。比對兩邊，確認 Supabase 收到的資料
又多又正確（預期每天 144 個時間點、完整度接近 100%）。

**階段二：GitHub Actions 改成「備援 + 警報」**（建議）
- **停止把資料 commit 進 git**（repo 不再越來越肥）。
- **備援收集**：每 15 分鐘用 Python（重用 `clean_data.py`）抓一次台電，直接寫進 Supabase。
  因為主鍵防重複，跟主收集程式同時寫也沒問題。這是一條**完全獨立的路**：
  就算 Edge Function 壞了，還有機會補到資料。
- **健康檢查**：檢查資料庫最新一筆資料是否超過 40 分鐘前。超過就讓這次執行「失敗」，
  **GitHub 會自動寄 email 通知你**。
- 需要在 GitHub repo 設定裡加兩個 Secret：Supabase 網址和 service role 金鑰。

如果覺得太複雜，最簡單的替代方案是**直接停用**（把 `schedule` 刪掉，只留手動按鈕），
但這樣就沒有備援和警報了。

## 5. 實作步驟（確認計畫後一步一步做）

| 步驟 | 內容 | 你要在 Supabase 網站手動做的事 |
|---|---|---|
| 1 | 建立專案 | 註冊、建立專案（地區選 **Tokyo**，離台灣最近）、記下資料庫密碼、選方案 |
| 2 | 建立資料表、規則表、時區 | 在 SQL Editor 貼上我寫好的 SQL，按 Run |
| 3 | 寫 Edge Function 並部署 | 在網站上建立 function（或在 Mac 用 Supabase CLI 部署） |
| 4 | 手動測試一次 | 在網站上按一次執行，到 Table Editor 看資料有沒有進來 |
| 5 | 設定 pg_cron 排程 | 開啟 pg_cron、pg_net 擴充功能；把金鑰放進 Vault；貼上排程 SQL |
| 6 | 匯入舊資料 | 貼上匯入 SQL；上傳原始檔到 Storage |
| 7 | 每日彙總 | 貼上彙總 SQL，用舊資料對照 `availability.py` 驗證 |
| 8 | 並行觀察 3～7 天 | 每天看一下「缺資料檢查」 |
| 9 | 改 GitHub Actions | 在 GitHub 設定 Secrets |
| 10 | 更新文件 | 更新 `docs/methodology.md`（資料收集方式、新增的備註規則） |

程式碼會放在 repo 的 `supabase/` 資料夾（SQL 檔和 Edge Function），
這樣所有設定都有紀錄，哪天要重建也做得到。
